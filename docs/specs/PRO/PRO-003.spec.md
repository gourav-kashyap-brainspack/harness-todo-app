# PRO-003 — Profile photo: add / change / remove

## Goal
Add the optional profile photo (F-003 add/change, F-004 remove) using **`react-native-image-picker`** with **both gallery and camera** sources (resolved decision). Wire it into the Profile Setup (PRO-001) and Profile edit (PRO-002) flows; persist only the resulting local file **uri string** through the STG `profileRepository` (`Profile.photo?`). Owns the camera/photo-library **permission** flow (rationale + denied-state handling) — the STG coherence gap (f) note: "PRO owns the image-picker/permission flow; STG persists only the uri string."

## Context links
- Source feature(s): F-003 (Update Profile Picture, P2), F-004 (Remove Profile Picture, P2) · `docs/requirements/REQUIREMENTS.md`
- Depends on: PRO-001 (profile store, setup form), PRO-002 (profile view/edit screen — the photo control lives in both the setup + edit surfaces).
- STG seam: `Profile.photo?: string` (optional uri) in `core/types/profile.ts`; persisted via `profileRepository.saveProfile`. STG persists ONLY the uri string — capture/permissions are PRO's.
- Design: avatar treatment in `design-system.md` (PRO-002 placeholder → real image here).

## Functional requirements
- **FR1 — Install & configure `react-native-image-picker`** (resolve current stable via `npm view`; RN-0.75-compatible; `npm install --legacy-peer-deps`). Native config both platforms: iOS `Info.plist` `NSCameraUsageDescription` + `NSPhotoLibraryUsageDescription` (clear rationale strings) + `pod install`; Android permissions as the lib requires (camera; media read on the relevant API levels). Record the resolved version in `stack.md` (librarian).
- **FR2 — Add / change photo (F-003):** from the Setup form (PRO-001) and the edit form (PRO-002), a photo control offers **Take Photo (camera)** or **Choose from Library (gallery)**. On pick → get the local file uri → set it on the profile (`photo`) → persist via `saveProfile` → the avatar shows the image. Handle picker cancel (no-op).
- **FR3 — Remove photo (F-004):** a **Remove** action clears `photo` (set to `undefined`) → persist → avatar reverts to the placeholder (initials / Feather `user` chip from PRO-002). Only shown when a photo exists.
- **FR4 — Permissions flow (PRO owns it):** request camera / photo-library permission at the point of use with a pre-prompt rationale where appropriate; on **denied**, show a friendly message (toast/inline) explaining how to enable it (Settings) and do NOT crash or hang. On **restricted/unavailable**, degrade gracefully (e.g. gallery-only if camera unavailable).
- **FR5 — Persist only the uri (coherence):** the `Profile.photo` field holds the local uri string; persistence stays through `profileRepository` (no direct MMKV; no image bytes in MMKV). Note: the uri points at a device file — treat a missing/instaled file defensively in the view (broken-image → placeholder).

## Non-functional requirements
- **Accessibility:** photo control + remove action labeled (`accessibilityLabel` "Add photo"/"Change photo"/"Remove photo") + roles; the avatar image has an appropriate label (or decorative); ≥48dp targets; denied-permission message announced.
- **Reliability:** cancel/denied/unavailable never crash. A stale/broken photo uri falls back to the placeholder.
- **Performance / privacy:** don't copy huge images into memory needlessly (use the picker's resize/quality options for a reasonable avatar size). The photo is local-only; never uploaded (no network).

## Platform divergence (iOS / Android)
- **The native-surface task.** iOS: `Info.plist` usage strings + `pod install`; permission prompts are OS-driven. Android: manifest permissions + runtime request (scoped-storage/media differences across API levels); camera intent. Action-sheet presentation differs (native `ActionSheetIOS` vs a themed menu on Android — use one cross-platform themed component or the picker's built-in). Test the permission denied path on both.
- **Docs-first (ADR-0035):** ground the CURRENT `react-native-image-picker` API + the exact permission keys/behavior for the installed major via Context7 before coding — its API + permission handling change across versions; don't code from memory.
