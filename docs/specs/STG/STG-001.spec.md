# STG-001 — Typed storage service (Zod-guarded MMKV · versioned · corrupt-recovery · hydration)

## Goal
Build the app's **single typed persistence primitive**: a generic, Zod-validated MMKV storage service that every domain (Profile, Tasks) persists through — no feature touches MMKV directly. It wraps each stored value in a light **`{version, data}` envelope**, **restores state on startup** (F-037), and **recovers gracefully from corrupt/invalid data by resetting to a safe default, never crashing** (F-038). It also ships the **store-hydration pattern** (how a Zustand store loads its persisted slice once at boot) that STG-002 + PRO + TSK reuse. This is the STG **anchor** — the Tier-1 storage/hydration mechanics.

## Functional requirements
- **FR1 — Storage service** in `mobile/src/core/services/` (e.g. `storage.ts` / `storageService.ts`): a typed API over one shared **default** `MMKV` instance:
  - `getItem<T>(key, schema: ZodSchema<T>, fallback: T): T` — read + JSON-parse + **unwrap the version envelope** + Zod-validate; on ANY failure (absent · malformed JSON · failed Zod · wrong version it can't handle · thrown read) return `fallback` (F-038), never throw.
  - `setItem<T>(key, schema, value): void` — Zod-validate the value, wrap in `{ version, data }`, JSON-stringify, write.
  - `removeItem(key): void`, `hasItem(key): boolean`.
  - Keys are declared as exported constants in one place (a `StorageKeys` registry) so there is a single source of truth for every persisted key (prevents key-string drift).
- **FR2 — Version envelope:** every value is persisted as `{ version: number, data: <validated> }`. `getItem` reads the envelope, checks `version`; on an unknown/older version with no handler → treat as corrupt → `fallback` (F-038). (No migration runners yet — light envelope only; the first real migration is added when a schema changes. Record this as the extension point.)
- **FR3 — Restore on startup (F-037):** a `hydrate`/`restore` helper + the **store-hydration pattern**: a Zustand store calls `getItem(key, schema, fallback)` **once at initialization** to seed its persisted slice, and persists back via `setItem` on mutation. Provide a small reference (a `createPersistedSlice`/`hydrateFromStorage` helper OR a clearly documented recipe) that STG-002/PRO/TSK follow verbatim. Hydration is synchronous (MMKV is sync) and must complete within the boot budget (well under the 3s cold-start NFR).
- **FR4 — Corrupt-data recovery (F-038):** the **decision of record is reset-to-safe-default** — a failed read returns the caller's `fallback` (empty list / null profile / default), emits a **dev-only** `__DEV__` warning (never a user-facing crash or error toast), and the app boots normally. A subsequent `setItem` overwrites the bad blob. No quarantine slot (deliberately simple for MVP; note it as a possible future extension).
- **FR5 — Default-instance adoption (spec-gap b):** the service uses `new MMKV()` (the same default instance FND's stores use). Do **NOT** rename or relocate `theme.mode` / `app.hasLaunched`. Document that FND's `themeStore`/`launchStore` MAY later be refactored to route through this service **without key churn** (optional consistency follow-up — not required by this task; their current raw usage keeps working because it's the same instance + same keys).
- **FR6 — No direct MMKV in features:** this service is the ONE place `react-native-mmkv` is imported for domain data. (The code-reviewer blocks a feature that imports `MMKV` directly — enforced at STG-002/PRO/TSK.)

## Non-functional requirements
- **Reliability:** never crash on corrupt/absent/partial data (F-038 / PRD §11 "recover from invalid data"). Every read path is total (returns a value for all inputs).
- **Performance:** synchronous MMKV reads; hydration adds negligible cold-start cost (a few small reads). No large synchronous blobs on the boot critical path.
- **Maintainability:** one service, one key registry, one envelope shape. Adding a new persisted domain = a schema + a key + a repository, never new MMKV plumbing.
- **Type-safety:** `getItem`/`setItem` are generic over the Zod schema; TS infers `T` from the schema (single source of truth for shape).
