# STG-002 — Profile + Task persisted schemas & repositories (+ hydration wiring)

## Goal
On top of the STG-001 storage service, define the app's **persisted domain model** — the **Profile** and **Task** Zod schemas + TS types (in `core/types`) — and the **typed repositories** (in `core/services`) that persist and restore them (F-006, F-036), plus the **hydration wiring** so a store loads them at boot (F-037). This is the single, shared data-access layer: PRO builds profile UI/logic on `profileRepository`, TSK builds task UI/logic on `taskRepository` — **neither touches MMKV or re-defines the shapes**. Establishes the repository pattern PRO/TSK reuse.

## Context links
- Source feature(s): F-006 (Persist Profile Data), F-036 (Persist Task Data) · also completes F-037 (restore) for these domains.
- Data model: `docs/requirements/REQUIREMENTS.md` → Data model (PRD §7.3).
- Depends on: STG-001 (`storage service` + `{version,data}` envelope + hydration helper + `StorageKeys`).
- Coherence check (STG, from `modules.json`): "Both Profile and Tasks persist through the single MMKV storage service — neither writes to MMKV directly or rolls its own persistence."
- Downstream consumers: `/module PRO` (profile), `/module TSK` (tasks).

## Functional requirements
- **FR1 — Persisted domain schemas** in `mobile/src/core/types/` (Zod schema + inferred TS type per model; the schema is the single source of truth):
  - **`Profile`**: `{ name: string (required, non-empty), email: string (required, valid email — per OQ-2 both required), photo?: string (optional local uri) }`. One profile per device.
  - **`Task`**: `{ id: string (uuid), title: string (required, non-empty), description?: string, status: 'active' | 'completed', dueDate?: string (ISO date, optional), createdAt: string (ISO), updatedAt: string (ISO) }`. **`id` is a `string`** (satisfies FND coherence spec-gap d — the nav `taskId: string` contract; generate via a uuid util).
  - Export the schemas AND the inferred types (`Profile`, `Task`) from `core/types` so PRO/TSK import the ONE definition.
- **FR2 — Profile repository** (`core/services`, e.g. `profileRepository.ts`) — F-006: `getProfile(): Profile | null`, `saveProfile(p: Profile): void`, `clearProfile(): void`. All via the STG-001 service (`getItem`/`setItem` with the Profile schema + a `StorageKeys.profile` key). Corrupt/absent → `null` (safe default, F-038 inherited from the service).
- **FR3 — Task repository** (`core/services`, e.g. `taskRepository.ts`) — F-036: `getTasks(): Task[]`, `saveTasks(tasks: Task[]): void` (persist the collection), and the granular helpers TSK will need (`upsertTask(task): Task[]`, `removeTask(id): Task[]`) implemented as pure transforms over the persisted array + a `saveTasks`. Corrupt/absent → `[]` (safe default). A `uuid` helper for new task ids (add `react-native-uuid` or `uuid` — resolve current stable — OR a crypto-based helper; keep it one util in `core/lib`).
- **FR4 — Hydration wiring (F-037):** demonstrate the STG-001 hydration pattern end-to-end for these domains — either a thin reference store or a documented `hydrate()` that seeds from the repositories at boot. The full Profile/Task **feature stores** (business logic, actions) are PRO/TSK's to build; STG-002 delivers the **repositories + the persisted types + the proven hydration recipe** they plug into. Make explicit what STG owns (persistence + shapes) vs what PRO/TSK own (feature state + screens).
- **FR5 — Single source of truth:** the Profile/Task Zod schemas + types live ONLY in `core/types`; the repositories are the ONLY persistence path. No duplicate shape or a second MMKV write anywhere (the code-reviewer blocks reinvention).

## Non-functional requirements
- **Reliability:** every repository read is total (corrupt/absent → safe default via STG-001) — no crash (F-038). Writes Zod-validate before persisting (reject/skip invalid rather than store garbage).
- **Maintainability:** adding a field = edit the one Zod schema; repositories + types follow. No shape drift between persistence and features.
- **Performance:** task collection persisted as one JSON blob (fine for the PRD's expected volume; note the "thousands of tasks" risk from §17 as a future pagination/index concern, not MVP).

## Test plan
### Unit
- `profileRepository.test.ts`: save→get round-trip; absent → `null`; corrupt/invalid persisted blob → `null` (no throw); `clearProfile` removes it; `saveProfile` rejects/guards a Zod-invalid profile (e.g. bad email).
- `taskRepository.test.ts`: save→get round-trips a Task[]; absent → `[]`; corrupt → `[]` (no throw); `upsertTask` adds a new task (with a generated string id) and updates an existing one by id + bumps `updatedAt`; `removeTask` drops by id; invalid task guarded.
- Schemas: Profile requires name + email (valid email); Task requires title + string id + status enum; optional fields optional.
- uuid util returns unique string ids.
### Maestro E2E (flows) — module-edge, local-only
- Behavioral coverage comes at the module edge via the assembled flows once PRO/TSK screens exist: create a task / profile → kill-relaunch → data restored (F-006/F-036/F-037); a corrupted store still boots to a safe empty state (F-038). No standalone STG flow.
