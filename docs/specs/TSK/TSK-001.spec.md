# TSK-001 — Tasks store + Home list

## Goal
Build the product's core surface: the **Tasks Zustand store** (the single source of task state, hydrated once from the STG `taskRepository`) and the **Home screen** that renders the task list (FlatList) with an empty state, a floating action button (FAB) to add, a personalized greeting, and pull-to-refresh (F-042). This is the TSK **anchor** — every later TSK screen/action reads from and mutates this one store. Displays all tasks (active + completed together, no filtering — search/filter/sort is ORG's module later).

## Context links
- Source feature(s): F-008 (View Task List), F-042 (Pull to Refresh) · `docs/requirements/REQUIREMENTS.md`
- STG seam: `mobile/src/core/services/taskRepository.ts` (`getTasks`/`saveTasks`/`upsertTask`/`removeTask`), `core/types/task.ts` (`Task`, `taskSchema`, `TaskStatus`). Hydration recipe: `createPersistedValue` / the PRO `profileStore` pattern.
- FND seam: the `Home` route + placeholder (`src/app/navigation/screens.tsx`), `Screen`/`EmptyState`/`LoadingIndicator` (`@/components/ui`), theme tokens, typed nav (`useAppNavigation`).
- PRO reuse: the profile name for the greeting (`useProfileStore`); the feature-store-hydrates-from-repository pattern (mirror `profileStore`).
- Conventions + patterns registry.

## Functional requirements
- **FR1 — Tasks store** (`src/features/tasks/store/taskStore.ts` — feature state; the SINGLE task-state source, coherence check 3): Zustand store `tasks: Task[]`, **hydrated once at init from `taskRepository.getTasks()`**. Expose the full action set (thin delegations to `taskRepository`, each takes the returned array and `set`s it) so later TSK tasks wire UI to them without a second store:
  - `addTask(input)` → `upsertTask` (new) · `updateTask(input)` → `upsertTask` (existing) · `removeTask(id)` → `removeTask` · `toggleStatus(id)` (active⇄completed) → `upsertTask` · `duplicateTask(id)` → `upsertTask` (copy) · `refresh()` → `getTasks` (re-read; for pull-to-refresh).
  - All writes go through `taskRepository` (never direct MMKV). `updatedAt` is bumped **once, in `taskRepository.upsertTask`** — never recomputed in the store or a screen (coherence check 2). TSK-001 may implement only the methods it needs now (refresh + the list read) but SHOULD define the store shape so 002/003/004/005 extend it, not fork it.
- **FR2 — Home screen** (`src/features/tasks/screens/HomeScreen`, replacing the FND placeholder on the `Home` tab): a `Screen` containing:
  - a **greeting** header (e.g. "Hi, {profile.name}" from `useProfileStore`; graceful if no name);
  - the **task list** — a `FlatList` over the store's `tasks`, each row a task item (title, status indicator, due date if set, a completed task shown with a check + muted/strikethrough style but **kept in position** — no auto-move, per OQ-8). Rows are tappable (navigate to Task Detail — the actual navigation lands in TSK-003; here the row is pressable and typed);
  - a **FAB** (bottom-right) to add a task (navigates to `AddTask` — screen built in TSK-002; here the FAB is wired to the route);
  - **empty state** — reuse `EmptyState` ("No tasks yet", friendly copy per PRD §7.8, an action/hint to tap +) when `tasks` is empty (F-030's primitive).
- **FR3 — Pull-to-refresh (F-042):** the FlatList `refreshControl` calls the store's `refresh()` (re-reads from `taskRepository`) — themed spinner (reuse the loading token/`LoadingIndicator` treatment). Since data is local, this is effectively a re-hydrate; keep it fast, no artificial delay.
- **FR4 — List performance:** `FlatList` (virtualized), stable `keyExtractor` (task `id`), memoized row component, no inline row re-creation. Ready for the "many tasks" case (PRD §17) though pagination is deferred.
- **FR5 — Task row component** (`src/features/tasks/components/TaskListItem`): presentational, tokens only, ≥48dp tappable, a11y-labeled (title + status announced). Reused by ORG later.

## Non-functional requirements
- **Performance:** virtualized list; memoized rows; store hydration synchronous at init (one repo read); smooth scroll (PRD §11).
- **Accessibility:** each row labeled (title + completed state, not color-alone — check icon + style); FAB labeled ("Add task"); greeting readable; ≥48dp; fontScale; contrast both themes. Visible text anchors for Maestro.
- **Reliability:** corrupt/absent tasks → `[]` (inherited from `taskRepository`/STG — never crash).

## UI / design notes
- Home: greeting + list + FAB, using `Screen` + tokens. The `design` agent supplies the visual spec (list row layout, completed-task treatment, FAB, greeting, empty state) reconciled with `design-system.md`; `frontend` implements. Completed = check + muted/strikethrough (never color-alone). Distinctive, not default-RN-slop.
- FAB: a `primary` circular button, bottom-right, safe-area aware, `accessibilityLabel="Add task"`.
- Note: search bar + filter chips (PRD §9 Home) are **ORG's** — do NOT build them here; leave room in the layout.

## Platform divergence (iOS / Android)
- FlatList `refreshControl` (RefreshControl) renders per-platform; FAB elevation (Android) vs shadow (iOS) via a themed helper. Safe-area for the FAB + list bottom inset.

## Offline / degraded network

## Accessibility
- Rows: `accessibilityLabel` = title + status; `accessibilityRole="button"` (tappable → detail). FAB labeled. Completed state conveyed by icon+style, not color alone. ≥48dp, fontScale, AA contrast both themes.
