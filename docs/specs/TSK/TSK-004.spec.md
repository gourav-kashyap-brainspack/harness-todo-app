# TSK-004 — Task lifecycle actions

## Goal
Wire the remaining task lifecycle into the UI: **mark completed / restore to pending** (F-013/F-014), **delete with a confirmation** (F-011/F-012, reusing PRO's `ActionSheet`), and **duplicate** (F-015). All act on the single `taskStore` (its action methods from TSK-001), surfaced on the Home list rows and the Task Detail screen.

## Context links
- Source feature(s): F-011 (Delete Task), F-012 (Confirm Task Deletion), F-013 (Mark Completed), F-014 (Mark Pending), F-015 (Duplicate Task)
- Depends on: TSK-003 (Detail screen exists) + TSK-001 (store actions + list rows).
- Reuse (PRO): the **`ActionSheet`** primitive (`@/components/ui`) for the delete confirmation (STG/PRO gap c — don't build a new Modal). Store actions `toggleStatus`/`removeTask`/`duplicateTask` (defined in TSK-001).
- STG seam: `taskRepository` (via the store); `updatedAt` bumped once in the repo.

## Functional requirements
- **FR1 — Complete / pending toggle (F-013, F-014):** a control on each Home list row (and on Task Detail) toggles the task's `status` active⇄completed via `taskStore.toggleStatus(id)` → `taskRepository.upsertTask` (bumps `updatedAt` once — check 2). Completed tasks stay in position (OQ-8) with the check + muted/strikethrough treatment (from TSK-001). Instant, optimistic (local write).
- **FR2 — Delete + confirm (F-011, F-012):** a delete affordance (on the row via swipe/menu and/or on Detail) opens the **`ActionSheet`** with a destructive **"Delete"** (danger styling) + **"Cancel"** — the confirmation (F-012). Confirm → `taskStore.removeTask(id)` → `taskRepository.removeTask`; the task leaves the list; if deleting from Detail, navigate back to Home. Cancel → no-op. **Never delete without the confirm.**
- **FR3 — Duplicate (F-015):** a duplicate affordance (row menu and/or Detail) → `taskStore.duplicateTask(id)` creates a NEW task: **same title (optionally suffixed "(copy)"), description, and due date; `status` reset to `'active'`; a fresh `id` + `createdAt`/`updatedAt`** (resolved decision — copy fields, reset status + timestamps). The copy appears in the list.
- **FR4 — Action surfacing:** decide + implement a coherent affordance model — e.g. a per-row overflow/long-press menu (an `ActionSheet` with Complete/Edit/Duplicate/Delete) and/or inline controls, plus the same actions on Detail. Keep it consistent across list + detail; reuse `ActionSheet` for menus/confirms rather than bespoke modals.
- **FR5 — Single store, no duplicate state:** all actions mutate the one `taskStore`; the list + detail reflect changes reactively (coherence check 3). No action recomputes `updatedAt` itself (check 2).

## Non-functional requirements
- **Accessibility:** every action labeled (`accessibilityLabel` "Mark complete"/"Delete"/"Duplicate"); destructive action marked (accessibilityRole + the danger styling, not color-alone); confirm dialog announced; ≥48dp targets. Maestro-anchorable.
- **Reliability:** delete is guarded by confirm (F-012); toggle/duplicate are idempotent-safe local writes.
