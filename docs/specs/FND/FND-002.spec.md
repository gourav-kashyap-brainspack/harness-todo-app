# FND-002 — Design system + theming (light + dark)

## Goal
Establish the product's visual foundation: a NativeWind/Tailwind **token system** (color, spacing, type scale, radius) with **both light and dark palettes** (dark mode is in MVP per OQ-10), a runtime theme controller (**system default + persisted manual override** per the resolved decision), and the `useTheme()` hook + `ThemeProvider` every screen consumes. This is the design **anchor** task — it sets the Tier-1 theming pattern; after this, no component hardcodes a hex color. Realizes **F-045** (light theme) extended to dark.

## Functional requirements
- **FR1 — Token source of truth in `tailwind.config.js`:** semantic color tokens (e.g. `bg`, `surface`, `card`, `text`, `text-muted`, `border`, `primary`, `primary-fg`, `success`, `danger`, `warning`) defined as CSS variables so a single set of utility classes resolves per active theme. Spacing scale, `borderRadius`, and a type scale (`text-xs…text-3xl` mapped to the product's sizes). **No raw hex in components — only tokens.**
- **FR2 — Light + dark palettes** in `global.css` via CSS variables: a `:root` (light) set and a dark set toggled by NativeWind's `dark` variant / a `data-theme`-equivalent root class. Both palettes meet WCAG AA contrast for text on their backgrounds.
- **FR3 — Theme controller (Zustand UI store, `core/store`):** state `mode: 'system' | 'light' | 'dark'` + derived `resolvedScheme: 'light' | 'dark'`. Default `mode: 'system'` → follows `useColorScheme()`. A manual override sets `mode` to `light`/`dark`. The chosen `mode` is **persisted via MMKV** (raw key, same minimal-storage approach as FND-004's first-launch flag; the typed STG service later can adopt it) and restored on boot.
- **FR4 — `ThemeProvider` + `useTheme()` hook** in `src/theme`: applies the resolved scheme to the NativeWind root (so `dark:` utilities activate), exposes `{ mode, resolvedScheme, setMode }`. Mounted in `AppProviders` (from FND-001).
- **FR5 — A `setThemeMode` action** exposed for a future toggle UI (the actual toggle control lives on the Profile screen — PRO — but the mechanism + store live here). Reacts live to OS scheme changes when `mode === 'system'` (subscribe to `Appearance`).
- **FR6 — Design tokens documented** in `docs/context/design-system.md`: the token names, their light/dark values, the type/spacing scale, and an initial **anti-patterns / banned-defaults** list (guards AI-slop: e.g. no pure-black `#000` text, no default RN blue, consistent 4pt spacing grid).

## Non-functional requirements
- **Accessibility:** text/background pairs pass **WCAG AA** in both light and dark; never convey state by color alone (pair with icon/label — enforced in FND-005).
- **Performance:** theme switch is instant (no reflow jank); no re-mount of the tree on toggle.
- **Maintainability:** adding a new semantic color = one token entry, not a per-screen edit.

## Platform divergence (iOS / Android)
- `useColorScheme()`/`Appearance` behave consistently on both; ensure status-bar style flips with the resolved scheme (light content on dark bg and vice-versa) — handled at the shell (FND-004) but the resolved scheme is sourced here.
- No `.ios/.android` split expected.

## Offline / degraded network
- Fully offline — theme is local-only. No network.

## Accessibility
- Contrast AA in both themes (verify the token pairs). The provider must not trap or break screen-reader focus. Respects `fontScale` (type scale uses scalable units).
