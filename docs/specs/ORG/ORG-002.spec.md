# ORG-002 — Search (title + description, real-time) + no-results

## Goal
Add **real-time search** over the task list (F-020 title, F-021 description, F-022 as-you-type) as a search bar on Home, feeding the **search** stage of the `selectVisibleTasks` pipeline established in ORG-001. Search **composes** with the active filter + sort (search ∩ filter → sort). Search text is **in-memory (resets on relaunch)**, per the resolved decision. When a search yields nothing, show the dedicated **no-search-results** empty state (F-031), distinct from the no-tasks and filtered-empty states.

## Context links
- Source feature(s): F-020 (Search by Title), F-021 (Search by Description), F-022 (Real-Time Search), F-031 (Display No Search Results).
- Depends on: **ORG-001** — the `taskQueryStore` (`search`/`setSearch`, already in-memory) + `selectVisibleTasks` (the pipeline with a search pass-through slot).
- Reuse: `EmptyState` (reuse-or-block — F-031 no-results) · `Screen`/`FlatList`/`TaskListItem` on Home · theme tokens · a search input (see UI notes — new small primitive or a features/tasks component).

## Functional requirements
- **FR1 — Search bar on Home:** a text input at the top of the list (in the ORG-001 organize header, in its reserved slot), bound to `taskQueryStore.search`/`setSearch`. Clearable (an × to reset to `''`). Placeholder e.g. "Search tasks". Keyboard: no submit needed — it filters live.
- **FR2 — Real-time (F-022):** results update **as the user types** — every keystroke re-derives `selectVisibleTasks`. For a local in-memory list this is instant; **no network, no async, no debounce required** (a list this size filters synchronously; do not add a backend call). If profiling ever shows jank on very large lists, a light debounce is a future optimization — not needed for MVP.
- **FR3 — Search predicate (F-020 + F-021):** implement the search stage of `selectVisibleTasks` — a task matches when the **trimmed, case-insensitive** query is a substring of its **title (F-020) OR description (F-021)**. Empty/whitespace query → no filtering (passthrough, as ORG-001 stubbed). Description is optional — a missing description simply doesn't match on that field.
- **FR4 — Composition:** search composes with the active filter + sort — the pipeline order is **search → filter → sort** (or an equivalent order that yields "matching ∩ filtered, then sorted"). Searching while filter=Active shows only active tasks matching the query, in the active sort order. Changing the filter/sort while a search is active keeps the search applied.
- **FR5 — No-search-results empty state (F-031):** when `search` is non-empty AND the derived list is empty, show an `EmptyState` with search-specific copy (e.g. title "No results", message "No tasks match '<query>'." or a generic "Try a different search."). This is **distinct** from ORG-001's no-tasks ("No tasks yet") and filtered-empty ("No completed tasks") states — pick the correct one by precedence: no tasks at all → no-tasks; else non-empty search with no matches → no-results (F-031); else filter matched nothing → filtered-empty. Reuse the `EmptyState` primitive (a fork is `[blocking]`).
- **FR6 — Search resets on relaunch:** `search` is in-memory (ORG-001) — confirm a relaunch clears it (the search bar is empty on cold start) while filter+sort persist.

## Non-functional requirements
- **Accessibility:** the search input `accessibilityLabel` "Search tasks"; the clear button labeled "Clear search"; ≥48dp; both themes; fontScale. Maestro-anchorable (search input + the no-results text).

- **Performance:** synchronous filter over the memoized selector; `TaskListItem` stays memoized; typing does not re-render the whole list beyond the necessary data swap.
