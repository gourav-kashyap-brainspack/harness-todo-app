## Accumulating project debt (tracked here as a standing risk, not a harness-machinery simplification candidate)
- **`app/navigation/hooks.ts` (`useAppNavigation`/`useAppRoute`) is now confirmed app-layer-only, not a general feature-screen helper.** The registry's "Typed navigation pattern" row describes these as the go-to for route-narrowing, but every feature screen that has actually needed route params or a typed nav prop (`ProfileSetupScreen`, `ProfileScreen`, `HomeScreen`, `AddTaskScreen`, and now TSK-003's `TaskDetailScreen`/`EditTaskScreen`) deliberately avoids importing them — `feature→app` is a disallowed `eslint-plugin-boundaries` direction — and instead uses plain `useNavigation()` + a locally-declared narrow `RouteProp` (now its own registry row, "Typed navigation inside a feature screen", established TSK-003). The hooks' **only** real consumer is `BootstrapScreen.tsx` (itself `app`-layer). Not urgent — nothing is broken, the boundary rule is being followed correctly — but a future architect pass should either re-scope the hooks' doc comment/registry description to "app-layer routes only" (cheap) or, if a genuine cross-feature typed-nav need never materializes, consider whether the dedicated helper module still earns its place over just inlining the one `BootstrapScreen` call site. State: **watch**. Evidence: grep across `mobile/src` (TSK-003 librarian pass, 2026-07-12) — 6 feature screens use the plain pattern, 1 consumer (`BootstrapScreen`) uses the app-layer helpers.
- **Deferred local E2E — 3 modules deep, 0 runs to date.** FND, STG, and PRO all declared `done` with `e2eStatus: deferred` (human decision each time — FND/STG were headless/no-UI, PRO deferred on the disk-pressure item above). Nothing has actually exercised the Maestro flows yet, even though PRO was the first module with a genuinely-runnable flow (fresh launch → Profile Setup → Home → view/edit/photo/theme). Recommend running the combined FND+STG+PRO flow suite at or before the TSK module edge — deferring a 4th module's worth of flows compounds the risk that an assembled-flow bug (not caught by any per-task unit gate) surfaces only at the mandatory pre-`development→main` E2E gate, far from the change that caused it.
