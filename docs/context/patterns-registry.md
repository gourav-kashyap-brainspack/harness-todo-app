# Canonical Patterns Registry — &lt;PROJECT_NAME&gt;

> **Tier-1 cross-cutting patterns** — the recurring *how* that must be identical across tasks (response envelope, DTO/validation style, auth guard, ownership checks, pagination, data-access, module layout, forms, async UI states…). Established by the first task that needs each, reused thereafter.
>
> **This file is split out of `conventions.md` to keep always-loaded context lean.** It is NOT `@`-imported — it is read on demand. **Builders, architect, code-reviewer, and librarian MUST `Read` this file before classifying / inventing / reviewing any Tier-1 pattern.** The *policy* that governs this registry (two-tier rule + roles) lives in `conventions.md` → "Pattern policy (two-tier)".
>
> **Maintained by the librarian** (append a row on task done). `ref:` = the reference implementation to copy. **Empty until the first foundation task lands** — the first task to solve a Tier-1 concern well establishes the pattern; every later task reuses it rather than re-deciding.

| Typed storage service (the ONE persistence path) | All domain persistence goes through `core/services/storage.ts`'s `getItem<T>(key,schema,fallback)`/`setItem`/`removeItem`/`hasItem` — no feature/domain code imports `react-native-mmkv` directly (code-reviewer blocks it). Every value is wrapped in a `{version,data}` envelope with a `migrate(version,data)` seam for future schema changes; every read is **total** (absent key · malformed JSON · non-envelope shape · unmigratable version · failed Zod parse · a thrown native read all fall back to the caller's `fallback`, never throw — F-038). Keys are declared once in the `StorageKeys` registry (single source of truth, prevents key-string drift). Two hard-won correctness rules for anyone extending this: **(a)** the "can't migrate this version" sentinel MUST be a `Symbol` (`UNMIGRATABLE`), never `null` — `null` is a legitimate persisted `data` value (e.g. a nullable Zod schema), so reusing it as a corrupt-marker would wrongly discard real data; **(b)** the corrupt/thrown-read path logs `error.name` only, never `String(error)`/`error.message`/the raw stored string — a `JSON.parse` error message can echo a fragment of the corrupt blob, which may contain PII once STG-002+ payloads (profile name/email) land | `mobile/src/core/services/storage.ts:getItem,setItem,removeItem,hasItem,StorageKeys,migrate` + `mobile/src/core/types/storage.ts:StorageEnvelope` | STG-001 | — |
| Store hydration pattern (Zustand ⇄ typed storage) | `createPersistedValue(key, schema, fallback)` returns `{hydrate, persist}`: a Zustand store calls `.hydrate()` once at store-init to seed its persisted slice (synchronous, safe on the cold-start path) and calls `.persist(value)` inside its mutator actions to write back. This is what STG-002 (Profile/Task repositories) and any later PRO/TSK persisted state copy verbatim — do not hand-roll a new hydrate/persist pair per store | `mobile/src/core/services/storage.ts:createPersistedValue` + `mobile/src/core/types/storage.ts:PersistedValue` | STG-001 | — |

Screens that need explicit route-narrowing use the typed `useAppNavigation<RouteName>()`/`useAppRoute<RouteName>()` helpers instead of importing `useNavigation`/`useRoute` directly. PRO/TSK screens reuse this — never re-declare param types or re-augment the global | `mobile/src/app/navigation/types.ts` + `mobile/src/app/navigation/hooks.ts:useAppNavigation,useAppRoute` | FND-003 | — |

| Persisted domain model (`core/types` + repository) | A persisted domain shape is declared exactly once — a Zod schema + its `z.infer` type in `core/types/<domain>.ts` — and the matching `core/services/<domain>Repository.ts` is the ONLY read/write path for it. | Repository pattern (total reads, validating writes, pure-transform mutations) | A repository's read is **total** (absent/corrupt → the caller's safe default via `getItem` — `null` for a singleton, `[]` for a collection — never throws); its write Zod-validates before persisting and throws on mismatch (a caller bug, e.g. an unvalidated form value, not corrupt storage — deliberately not swallowed). A collection repository adds `upsertTask(input)`/`removeTask(id)` as **pure transforms**: read the full collection, compute the next array, persist it, return it — callers never touch MMKV or hand-diff the array. `upsertTask` on an existing id is a **wholesale field replace**, not a partial patch — any edit-form caller must submit the full set of business fields, not just the changed ones | `mobile/src/core/services/taskRepository.ts:upsertTask,removeTask` + `mobile/src/core/services/profileRepository.ts:getProfile,saveProfile,clearProfile` | STG-002 | — |
| ID generation (`newId()`) | One id-generation util for the whole app, `core/lib/id.ts:newId()` (`react-native-uuid` v4 — pure JS, no native linking, no `react-native-get-random-values` polyfill). Any repository/store minting a fresh persisted-entity id calls this rather than hand-rolling a `Math.random()`/timestamp id. **Caveat — carry this whenever `newId()` is reused:** `react-native-uuid` is `Math.random()`-backed, **NOT a CSPRNG**. Use it only for internal/non-security entity ids (task ids, list-item keys). A security-sensitive token (auth, session, password-reset) needs a real CSPRNG (`uuid` + `react-native-get-random-values`, or `react-native-quick-crypto`) — never reuse `newId()` for that | `mobile/src/core/lib/id.ts:newId` | STG-002 | — |
