# Canonical Patterns Registry — &lt;PROJECT_NAME&gt;

> **Tier-1 cross-cutting patterns** — the recurring *how* that must be identical across tasks (response envelope, DTO/validation style, auth guard, ownership checks, pagination, data-access, module layout, forms, async UI states…). Established by the first task that needs each, reused thereafter.
>
> **This file is split out of `conventions.md` to keep always-loaded context lean.** It is NOT `@`-imported — it is read on demand. **Builders, architect, code-reviewer, and librarian MUST `Read` this file before classifying / inventing / reviewing any Tier-1 pattern.** The *policy* that governs this registry (two-tier rule + roles) lives in `conventions.md` → "Pattern policy (two-tier)".
>
> **Maintained by the librarian** (append a row on task done). `ref:` = the reference implementation to copy. **Empty until the first foundation task lands** — the first task to solve a Tier-1 concern well establishes the pattern; every later task reuses it rather than re-deciding.

| Typed navigation pattern | Route params typed once via `RootStackParamList`/`TabParamList` + a `declare global { namespace ReactNavigation { interface RootParamList extends RootStackParamList {} } }` augmentation (v6 "dynamic"/JSX-navigator typing — not the v7+ static-config API), so every bare `useNavigation()`/`useRoute()` call app-wide infers `RootStackParamList` with no per-call generic. Screens that need explicit route-narrowing use the typed `useAppNavigation<RouteName>()`/`useAppRoute<RouteName>()` helpers instead of importing `useNavigation`/`useRoute` directly. PRO/TSK screens reuse this — never re-declare param types or re-augment the global | `mobile/src/app/navigation/types.ts` + `mobile/src/app/navigation/hooks.ts:useAppNavigation,useAppRoute` | FND-003 | — |
| Navigation theming from tokens (native-chrome RGB exception) | `buildNavigationTheme(resolvedScheme)` maps the resolved app scheme to React Navigation's `Theme` (flat color strings, not `className`). Native-only chrome (nav container/tab-bar tint, OS status bar) can't consume NativeWind's CSS-variable indirection, so RGB triplets are copied **verbatim** from `design-system.md`'s color tables into ONE source, `src/theme/nativeChromeColors.ts` (`NATIVE_CHROME_RGB` + `rgbFromTriplet`) — `navigationTheme.ts`, `TabNavigator.tsx`, and `ThemeProvider.tsx`'s StatusBar all consume that single map. A palette change is one edit here, never per-consumer copies. **This is the one place to add a new native-chrome color** — do not hand-roll another RGB map for a native-only surface | `mobile/src/theme/nativeChromeColors.ts:NATIVE_CHROME_RGB,rgbFromTriplet` + `mobile/src/app/navigation/navigationTheme.ts:buildNavigationTheme` | FND-003 | — |
| Themed StatusBar (OS chrome, not nav chrome) | The OS status bar (glyph color + Android background) is rendered from `ThemeProvider`, not from the navigator — `NavigationContainer`'s `theme.dark` only styles React Navigation's own chrome (headers/tab-bar/background), it does not drive the OS status bar. Flips `barStyle`/`backgroundColor` with `resolvedScheme`, reusing the same `NATIVE_CHROME_RGB` source above, so it holds even before/without a navigator mounted | `mobile/src/theme/ThemeProvider.tsx:ThemeProvider` | FND-003 | — |
